# tests/e2e — the real pipeline, end to end

Runs a real computational code, feeds its output to the **real**
`scripts/eccejobmonitor`, and runs the **real** `scripts/parsers/*`
scripts on the blocks the monitor actually emitted.

```
tests/e2e/run_tests.py              every case whose code is installed
tests/e2e/run_tests.py -v           show each check
tests/e2e/run_tests.py --case NAME  one case
tests/e2e/run_tests.py --keep       keep the work directories to inspect
```

## Why this exists alongside tests/parsers

`tests/parsers` is fast, needs no code installed, and pins exact values
against captured outputs. It drives `eccejobmonitor_sim.py`, a
reimplementation of the monitor's Begin/Skip/End algorithm.

That leaves two holes it cannot close by construction:

**A bug in the monitor itself.** There has been one: `parseTypes ALL`
was compared case-sensitively against the uppercase string `Launch.C`
passes, so every not-yet-enabled descriptor was silently deleted and
trace properties (`GEOMTRACE` and friends) were never extracted during a
run. A simulator agreeing with itself will never find that class.

**A code changing its output.** Captured fixtures are frozen, so a new
release that rewords a section stays invisible. Gaussian 16 dropped
"atomic" from "Mulliken atomic charges" and that property was silently
never extracted again, for every G16 job, with no error anywhere (#80).

This suite's fixtures are therefore **input decks, not captured
outputs**. The output is regenerated by the code on every run, so
rewording shows up as a failed assertion here.

## The pipeline, and the seam that matters

```
  1  real code          runs the stored input deck
  2  eccejobmonitor     real Begin/Skip/End matching and real framing
  3  parser scripts     run on the blocks the monitor emitted
  4  assertions         what the calculation should contain
```

The monitor **does not run the parser scripts**. It matches blocks and
ships the raw block text; the client does the rest —
`JobParser::storeProperty` runs `<script> <parseArgs> >parseOut
<parseIn`. Stage 3 stands in for that C++ client, and the split has to
stay or the test stops resembling the product.

It also runs the monitor with **`-parseTypes ALL`**, uppercase, exactly
as `Launch.C` passes it. Lower-casing that here would hide the bug the
stage exists to keep fixed.

### Running the monitor outside ECCE

It looks like it needs the whole stack and does not:

```
perl scripts/eccejobmonitor \
  -commType stdio -monitoringMode post \
  -jobOutputFile job.out -parseDescriptorFile scripts/parsers/<code>.desc \
  -parseTypes ALL -outputFile results.out -calcName x -logFile monitor.log
```

`-commType stdio` drops the socket and the JMS dispatcher;
`-monitoringMode post` runs it over a finished file. No data server, no
gateway, no display.

`results.out` is the wire format, not text: `\001`, a sequence digit,
a 4-digit length, then a NUL-separated payload, with newlines mapped to
`\002`. `pipeline.unpack()` decodes it, reassembling multi-packet
properties first — a coefficient matrix exceeds `msgLength` and arrives
split, so treating each packet as a message truncates exactly the
properties most worth testing.

## Assertion style

Loose about exact numbers, strict about structure. Pinning an energy to
ten digits makes the suite fail on a code upgrade for a reason nobody
needs to care about. Pinning that `ORBSYM` has the same length as
`ORBENG` catches the class that actually bites: `MoPanel::fillTable()`
reverses the energy, occupancy and symmetry vectors independently and
indexes all three by the same row, so unequal lengths do not run out at
the end — they shift, and mislabel every row.

Where a number *is* pinned it should be one that means something: the
lowest CH4 orbital near −0.92 Hartree would read −25 if the eV
conversion were dropped, and `ENTHALPY − ETHERM` must equal RT exactly.

A code that is not installed is **skipped with its name printed**, never
silently passed, and a run where nothing at all was found exits 2 — "no
codes installed" must not read as "everything is fine".
