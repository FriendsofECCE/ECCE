# MO diagram golden dumps

A byte-identity oracle for the MO diagram engine (`MoDiagramPanel::build()`
and the model it hands to `MoDiagramCanvas`), captured from the *real* app
against real, stored calculations. It exists so a later refactor that moves
the engine out of wx and into a plain library can be checked against actual
behaviour rather than against a re-derivation of what that behaviour is
believed to be -- the refactor is trusted only as far as it reproduces
these dumps verbatim.

## What's here

- `fixtures/<name>/` -- calc directories in the same format `tests/apps`'
  `fixture.install()` copies into the fixture data-server account, trimmed
  to just what the MO diagram needs: `Parameters/chemsys.mvm` and
  `BasisSet.ecce_basisset` (the calc's chemistry system and basis --
  `gbsConfig()`/`EspField::overlapOf()` need both to compute the real
  overlap matrix), `Inputs/` (kept for realism, not read by the diagram),
  and only the `Props/` keys `MoDiagramPanel`/`MoAoOrder` read: `ORBENG`,
  `ORBOCC`, `ORBSYM`(+`BETA`), `MO`(+`BETA`), `MOAOORDER`. `Outputs/` is
  dropped throughout, same as `tests/apps/fixtures/calc-water-vib` --
  nothing in the property pipeline reads it, and it is the biggest part of
  a calculation.
  - `orca-co`, `gaussian-co` -- the same CO molecule from two codes/basis
    sets (ORCA HF/def2-SVP, Gaussian-16 RHF/def2SVP 6D 10F), C4v.
  - `gaussian-water` -- Gaussian-16, `NoSymm`, C2v detected from geometry
    alone (no ORBSYM in the stored data).
  - `nwchem-water` -- NWChem B3LYP/aug-cc-pVDZ-ish water, C2v, WITH ORBSYM.
  - `orca-crco6` -- ORCA RHF Cr(CO)6, Oh, the project's primary ligand-
    field reference case (see CLAUDE.md's MO-diagram section and
    `crco6-targets.md` in the working scratchpad). Its `Props/MO`,
    `ORBENG`, `ORBOCC` and `MOAOORDER` are NOT copied from the live
    account -- the stored copy there predates commit `7bfa419` (the ORCA
    per-atom angular-momentum reordering fix) and its MO coefficients are
    not correctly aligned to ECCE's basis-function order. They were
    regenerated by re-parsing `crco6.orcaout`'s `MOLECULAR ORBITALS` block
    through the CURRENT `scripts/parsers/orca.mo`, fed exactly the lines
    `scripts/eccejobmonitor` would feed it per `orca.desc`'s `[MO]` entry
    (`Begin=MOLECULAR ORBITALS`, `Skip=2`, `End=MULLIKEN POPULATION
    ANALYSIS` -- i.e. lines 901-7806 of that output). See "crco6 residual
    normalisation" below for what checking that reparse against the real
    overlap matrix found.
  - `calc-water-vib` is NOT duplicated here -- `capture.py` points
    straight at `tests/apps/fixtures/calc-water-vib` (Gaussian-16 water,
    STO-3G, opt+freq, C2v), reusing it rather than a second copy.
- `expected/<name>.dump` -- the golden `ECCE_MODIAGRAM_DUMP` output for
  each fixture, captured from the real `builder` binary at commit
  `809fbae` (headless, `ECCE_OPEN_PANEL="MO Diagram"` +
  `ECCE_EXIT_AFTER_DUMP=1`). Confirmed byte-identical across two
  independent captures of every fixture (`--repeat 2`), including
  `orca-crco6` (199 orbitals, ~30s to build).
- `capture.py` -- reproduces the above; see its own docstring for usage.
  Generalises `tests/apps/fixture.py`'s `install()` to take an explicit
  `source_dir` rather than duplicating its account/auth/`.htaccess`
  plumbing (`tests/apps`' own callers are unaffected -- `source_dir`
  defaults to `None`, which is the old behaviour).

## Findings from the captured dumps (2026-09-28)

**Capture against the tree's own `data/` and `scripts/`, not an install's.**
The first capture used an overlay whose `data/` linked to `/opt/ecce`,
which predates the `.edml` fixes in dbd022e/7bfa419. It showed Gaussian
CO's pi at 0.9926 and Cr(CO)6 residuals that looked like a within-shell
ordering bug, and both were just the stale files. The overlay must link
`data -> <repo>/data`, `scripts -> <repo>/scripts` and
`bin/builder -> <repo>/build-cmake/builder`.

- Groups and constructions: C2v (both waters, including Gaussian NoSymm
  with labels computed from the orbitals), C4v (both CO), Oh (Cr(CO)6,
  metal and six ligand donor sets). Full-group labels cover every drawn
  level in every fixture.
- `norm` (cT S c): exactly 1.0000 on every drawn level of every fixture
  except `nwchem-water`, which is 0.9994-1.0010. That fixture needs
  `Props/GEOMTRACE`, because NWChem reorients the molecule (autoz) and
  the coefficients are in its frame, not the input frame stored in
  chemsys. Without it the norms were 0.39-3.30. The residual ~1e-3 is
  consistent with NWChem's printed precision.
- Cr(CO)6: t2g and eg sets are labelled, the HOMO is 2T2g and metal-heavy,
  and there are three t2g levels (the pi-acceptor pattern of Albright
  et al. 2013, sec. 15.3).
- Cr(CO)6 metal column: fixed. It had drawn 3d T2g at -3.70 Ha and split
  3d across two rows. placeFragments()' one-row snap averaged a placed
  level with an unplaced one still holding its tabulated eV, and the
  shell-order step ran before the unconnected-level fallback. Now 3d
  (-0.21) < 4s (0.19) < 4p (0.27), all inside the molecular range.
- Still wrong in Cr(CO)6, both about which lines are drawn:
  1. Eg (3d) links to no molecular orbital, so the eg/eg* interaction
     (Delta_o) is missing. composeLevels() uses plain c^2, which gives Cr
     only 0.04-0.13 of the eg MOs (the Löwdin share of 5Eg is 0.52), so
     connect()'s 0.05 cutoff draws them to the ligands only.
  2. 4p (T1u) links only to 2T1u at -2.246 Ha, which is Cr's 3p semicore
     (99% on Cr). The core cutoff (-3.49) leaves it visible.

## Reproducing

```
ECCE_TEST_STATE=<fresh dir> ECCE_TEST_HOME=<overlay> python3 tests/modiagram/capture.py
```

Requires a private `builder` build/install exactly as `tests/apps` does
(see `tests/apps/README.md`) -- an overlay directory that symlinks
everything from a real install except `bin/builder`, which points at a
freshly-built `build-cmake/builder`. Add `--update` to (re)write the
goldens after an intentional engine change, and `--repeat N` to check
determinism before trusting a capture (used here with `N=2` for every
fixture). A single fixture can be named on the command line to avoid
re-running all six.
